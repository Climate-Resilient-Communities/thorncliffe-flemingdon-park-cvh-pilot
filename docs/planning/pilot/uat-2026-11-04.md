# UAT findings of 2026-11-04 and what was done

QA compared the pilot against the clickable prototype (climate-resilient-communities.github.io/thorncliffe-flemingdon-park-cvh-pilot). This page answers each finding: what changed, or why it did not, and how to check it. The changes are on the branch `claude/repo-overview-oypa2p`.

Three kinds of answer:

- **Fixed**: built in this round.
- **Not in the pilot**: the pilot PRD (`docs/planning/pilot/prd.md`, section 6.3) defers it to the MVP. Building it is a scope decision for the product owner, not a bug fix.
- **Already built, not reachable by QA**: the screen exists but needs a role or a step QA did not have.

## Seeing the ambassador screens

An Admin sets up a test ambassador. No code is needed.

1. Sign in as an Admin. Open **People** and use **Add a person**: Role **Ambassador**. Note the username and starting password; the starting password works once, within 72 hours.
2. Open **Coverage**, choose a test building and assign the new person to some of its floors.
3. In a second browser (or a private window), sign in as that person and choose a password. An ambassador needs no authenticator.
4. The Hub opens on **My building** (A-01). **Post a building update** (A-02, then A-03) and **My round** (A-04) are in the menu.
5. An ambassador's post is a real alert. Some kinds go on the web for residents at once, before anyone approves them (`src/modules/alerting/domain/d1.ts`), and texts follow a second person's approval. Post only on a test or staging environment. On production, open the screens without submitting.
6. Remove the test person's assignments, or the person, when QA is done.
